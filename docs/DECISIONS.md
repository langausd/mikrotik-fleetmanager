# Design-Entscheidungen (ADR-Log)

Die Entscheidungen fielen interaktiv: D1–D20 am 2026-09-11, danach in Runden (Abschnitte mit Datum). Pro Entscheidung:

## Architektur des Frameworks

| # | Thema | Optionen | Entscheidung / Konsequenz |
|---|-------|----------|---------------------------|
| D1 | Verteilung | **Pull + Push-Trigger** · reiner Push per SSH · HTTPS-Pull aus Container | Geräte holen per SFTP (Scheduler + Boot), der Manager stößt per `/system ssh-exec` sofort an. **Ergänzung:** Die aktive Config jedes Geräts (Export) liegt zentral in `state/<name>/`. *Umsetzung angepasst:* Der Manager holt Status und Export ab (Manager-Tick, `mgrTick`, Standard 10 min), weil ein Upload durch die Geräte die Policy `write` erfordern würde und damit SSH-Konfigurationsrechte am Manager. |
| D2 | Apply-Engine | **Daten + Reconciler mit Tags** · idempotente Befehlsskripte · Full-Rebuild per Reset | Jedes verwaltete Objekt trägt `comment="cfm:<typ>:<key> …"`. Getaggte Objekte ohne Datensatz werden entfernt (VLAN löschen = Zeile löschen). Ungetaggte Objekte werden nie angefasst. |
| D3 | Datenformat | **RouterOS-Arrays (.rsc)** · JSON + `:deserialize` | Native Arrays, per `/import` geladen, keine Parser-Abhängigkeit. |
| D4 | Source of Truth | Git lokal + Deploy · **nur auf dem Manager** · Git-Server im Container | Editiert wird in `cfm/work/` auf dem Manager. Historie über Archiv-Snapshots + externen Git-Hook (D13). Dieses Projektverzeichnis ist Seed/Referenz. |
| D5 | Release | **explizites Release** · automatisch nach Ruhezeit | `$cfmRelease` prüft Syntax, friert `work/` als `archive/<ver>/` ein, erzeugt Manifeste, triggert Push. Halbfertige Edits kommen nie an. |
| D6 | Geräte-Spezifika | **Schichten + lokaler Hook** · nur Parameter im Hostfile | global → Rolle → `hosts/<name>.rsc` → optional `hosts/<name>.post.rsc`. **Ergänzung:** Audit-Lauf zeigt von Hand angelegte Objekte an und kann sie gezielt als `cfm-override` markieren oder entfernen. |
| D7 | Manager-Redundanz | **Fallback-Liste** · VRRP-VIP | Geräte probieren Manager der Reihe nach. Backup spiegelt Primary (Pull) und ist read-only bis zur Beförderung. |
| D8 | Schutz vor kaputter Config | Backup + Watchdog · nur Pre-Apply-Export · **Canary-Ringe + Backup/Watchdog** | Ring 0 → 1 → 2. Promotion automatisch nach Erfolg + Soak-Zeit oder manuell (`$cfmPromote`). Pro Gerät: Backup vor Apply, Watchdog-Rollback per `/system backup load`, Version wird als `bad` gemerkt. |

Umsetzungsdetails:
* **Onboarding-VLAN 88 = `192.168.88.0/24`**, bewusst passend zur Werks-IP `192.168.88.1` neuer Geräte. Gateway `.250` (Router), DHCP `.100–.199` vom Primary-Manager (für Geräte mit DHCP-Client in der Werks-Config, z.B. APs im CAPs-Modus). Die Manager erreichen die Geräte direkt auf Layer 2 und haben dort die Host-Adresse ihrer MGMT-IP.
* **Zweistufiger Push:** Stufe 1 (Probe) liest Seriennummer/Modell/Version und stößt ggf. das Update an. Stufe 2 lädt den gerätespezifischen Bootstrap hoch und setzt das Gerät per `reset-configuration no-defaults=yes run-after-reset=` auf eine leere Config mit genau diesem Bootstrap zurück (keine Werks-Firewall/-DHCP-Reste). Danach läuft das normale `$cfmEnroll`.
* **Immer nur eine Onboarding-Sitzung gleichzeitig** (alle Werksgeräte haben `192.168.88.1`).
* **Werksgeräte findet der Manager unter `192.168.88.1` oder über ihre DHCP-Lease** im Onboarding-VLAN.
  Geräte mit PoE-Eingang nur an ether1 (hAP) starten dafür im CAPs-Modus (Reset-Taster ~10 s): Dort
  ist ether1 ein Management-Port mit DHCP-Client ohne Firewall, statt WAN-Port mit Firewall.

## Planung eines größeren Heimnetzes (Runde 2026-09-17)

| # | Thema | Optionen | Entscheidung / Konsequenz |

| D37 | Routing auf CRS-Switches mit L3-Hardware-Offloading | Routing im Switch-Chip ohne VRRP, Filter nur zustandslos per Switch-Regeln, Gäste/IoT per Regel zur CPU · Hybrid: vertrauenswürdige VLANs im Switch-Chip, Gäste/IoT auf einem CPU-Router · **alle VLANs über VRRP-Router in der CPU** | Laut MikroTik-Doku gibt es mit L3-Hardware-Offloading kein VRRP (dafür muss `l3-hw-offloading` am Switch ganz aus sein), die Chips kleinerer CRS3xx (z.B. 98DX3236, 98DX226S) können außerdem weder NAT noch Fasttrack im Chip, und die CPU-Firewall sieht im Switch-Chip gerouteten Verkehr nicht. ## Umsetzungsentscheidungen (technisch begründet, nicht separat abgefragt)

* **Sperre `cfmApplyBusy` (Labor 2026-10-11/12):** Auf dem Manager teilen sich der Agent und die
  Manager-Funktionen dieselben globalen Variablen (`$cfmG`, Bibliothek). `$cfmLoadData` (fast jeder
  Manager-Befehl, der Tick) importierte `global.rsc` neu – fiel das in einen Apply des Managers selbst,
  lief `base` ohne die Werte aus seinem Hostfile (`adminUser`, `mgmtExtra`, Ports): Im Labor sperrte
  cm1 so admin und den Zugang vom Host, nachgestellt mit Push plus parallelem `$cfmLoadData`.
  `$cfmImportAll` setzt die Sperre für die Dauer des Apply (auch im Probelauf), `$cfmLoadData` wartet,
  solange sie gesetzt ist und ein Job `cfm-agent` läuft (höchstens 120 s, dann Warnung). Keine Rolle
  ruft Manager-Funktionen auf, eine Selbstblockade gibt es nicht. Labor: `e2e.sh` Schritt 14i.
* **Gegenrichtung: Zeitstempel `cfmMgrData` (Review 2026-10-12):** `cfmApplyBusy` schützte nur einen
  Apply, der schon lief, wenn ein Manager-Befehl begann. Startet der Apply erst während `$cfmCheck` oder
  `$cfmShow`, importieren diese weiter die Hostfiles anderer Geräte in `cfmHost`, den der Apply gerade
  liest (cm1 bekäme z.B. die Ports von sw1). `$cfmLoadData` setzt deshalb einen Zeitstempel und gibt ihn
  am Ende frei; mit `hold=yes` hält ihn der Aufrufer, und `$cfmCheck` frischt ihn vor jedem Hostfile auf.
  `$cfmImportAll` wartet, solange er jünger als 30 s ist (höchstens 120 s), und erst danach setzt es
  `cfmApplyBusy` – andersherum warteten beide aufeinander. Ein Zeitstempel statt eines Flags, damit ein
  abgebrochener Befehl nichts dauerhaft sperrt. Labor: `e2e.sh` Schritt 14j.
* **Probelauf der Rolle `router` vor dem ersten VRRP (Probelauf des Router-Umzugs, 2026-10-11):** Die
  Rolle fragte für den DHCP-Server den Zustand des VRRP-Interface ab; im Probelauf ist es noch nicht
  angelegt, der Lauf brach ab. Fehlt es, gilt das Gerät jetzt als „nicht Master“ (DHCP aus), wie beim
  ersten echten Apply bis zur VRRP-Wahl. Labor: `e2e.sh` Schritt 6 (VLAN mit DHCP, kein Fehler).
* **Eigene Radios eines Wi-Fi-7-CAPsMAN (D53, 2026-10-03):** Ab Werk hängen die Radios des hAP be³
  am statischen, abgeschalteten MLD `mld1`; ohne MLO blieben sie nach dem Provisionieren aus. Wie die
  Rolle `ap` (D46) löst `$cfmCapsmanOn` sie davon, bevor sie die eigenen Radios provisioniert.
* **Dateizugriff über den Namen (TODO 21, D59):** `/file/find` wertet jede Datei in `/file` aus (Hardware ~0,2 ms je Datei; CHR mit 600 Dateien 8 ms je Suche), `/file/get <Name>` braucht 0,05 ms. `cfmRead`/`cfmWrite`/`cfmFileEx` und alle Prüfungen auf einen bekannten Namen greifen deshalb direkt zu; `cfmMB` merkt sich die Ablage je Sitzung (`cfmMBv`). Suchen per Regex bleiben, wo mehrere Dateien gemeint sind (Release, Archiv, Spiegel). `archiveKeep` ist jetzt standardmäßig 5. `$cfmRelease` lädt den Prüfer (`lib/mgr-check.rsc`) aus `work/`, bevor er prüft: Nach einem Framework-Update kannte der installierte die neuen Kennzeichen nicht und hielt das erste Release auf (`force=yes` nötig). Der Prüfer nutzt deshalb nur Helfer, die es auch in älteren Manager-Modulen gibt. Nachtrag 2026-10-11: Auf den Geräten greifen jetzt auch `base` (Prüfung auf `authorized_keys.<user>`) und der Agent (Flash-Ablage) über den Namen zu. Beim Apply war die Dateisuche aber nicht der Zeitfresser, sondern die SFTP-Abrufe mit je mindestens 1 s: Der Agent lädt nur noch geänderte Dateien (D69, Abschnitt „Straffung und Laufzeit“).
* **Rolle `router` mit VRRP (Laborprobe des Router-Umzugs, 2026-10-01, `e2e-vrrp.sh`):** Verkehr an
  die VIP kommt über `vrrp<VID>` herein, nicht über `vlan<VID>` – die Zonen-Firewall verwarf deshalb
  allen gerouteten Verkehr der Clients (sie nutzen die VIP als Gateway). Die VRRP-Interfaces stehen
  jetzt in derselben Zonen-Liste wie ihr VLAN, das des WAN-VLANs auch in `WAN`. Die reale Adresse
  (.250 + routerId) sucht die Rolle über Interface **und** Adresse – auf einem Router, der zugleich
  Primary-Manager ist, übernahm sie sonst dessen Onboarding-Adresse, und beide Rollen setzten sie bei
  jedem Apply hin und her. Im Onboarding-VLAN schalten die VRRP-Skripte keinen DHCP-Server mehr (dort
  vergibt der Primary-Manager; `on-backup` schaltete ihn ab).
* **Zurückgestellt (2026-10-01):** WebFig per HTTPS (TODO 25) bis Let's Encrypt über acme-dns mit einer öffentlichen Domain steht; Disk-Logging für den Primary (TODO 22), weil ein externer Syslog-Server geplant ist.
* **Dienst `reverse-proxy` (TODO 30):** steht in der Dienstliste der Rolle `base` wie `www-ssl`, ist also aus, sofern `services` ihn nicht nennt. RouterOS 7.2x schaltet ihn ab Werk auf Port 443 ohne Adressbeschränkung ein; ältere Versionen kennen ihn nicht (`$cfmSet` findet dann nichts). `$cfmCheck` meldet unbekannte Dienstnamen (z.B. `http`) und doppelte Ports in `services` als Fehler.

* **Manager-Bootstrap auf leerer Config:** `bootstrap-manager.rsc` setzt das Gerät mit `clean="yes"` zuerst per `reset-configuration no-defaults=yes keep-users=yes run-after-reset=` zurück und läuft danach selbst weiter; `keep-users` erhält User, Passwörter und SSH-Schlüssel. Das run-after-reset-Skript läuft als Systemnutzer `*sys` ohne SSH-Schlüssel, und die Dienste starten erst nach ihm (siehe Eigenheiten). Deshalb richtet es nur `post`, den MGMT-Zugang und den User cfm mit einem Einmal-Passwort ein. Ein Scheduler lädt nach dem Hochfahren per SFTP mit diesem Passwort eine `.auto.rsc` an 127.0.0.1 hoch, die RouterOS als cfm ausführt; sie legt einen Scheduler an, der cfm gehört und den eigentlichen Bootstrap samt Selbst-Enroll ausführt. Danach bekommt cfm ein neues Zufallspasswort. Die Stufen erkennt die Datei an Markierungsdateien, Fortschritt und Fehler stehen im Log. So bleiben keine Reste einer Werks- oder CAPs-Config; auf einem bestehenden Manager wird der Reset verweigert. Verworfen: ein zweiter Import von Hand nach dem Reset (einfacher, aber nicht automatisch).
* **Lokale Site anlegen:** `tools/new-site.py` erzeugt ein Overlay aus den Beispieldaten samt `STAND.md` (aktueller Stand, Logbuch mit den neuesten Einträgen oben, nächste Schritte, offene Punkte; ausführliche Analysen in einer `BEFUNDE.md` daneben) und ausgefülltem Bootstrap-Kopf; das Manager-Hostfile enthält nur den Uplink, weil Ports, die es auf dem Gerät nicht gibt, den Apply scheitern ließen. `tools/upload-seed.sh` lädt aus einem Overlay nur `*.rsc` (außer `bootstrap*.rsc`, die per `--bootstrap` einzeln ins Wurzelverzeichnis geht), `authorized_keys.<user>` und `hosts/`, `roles/`, `lib/`, `meta/` – die Site-Daten (Dateien direkt in `work/` und `work/hosts/`) seit D72 nur mit `--site`; Notizen (`STAND.md`, `BEFUNDE.md`) und CSV-Listen bleiben lokal (vorher landeten sie in `work/` und damit in jedem Release). `meta/inventory.rsc` geht nur mit `--seed-inventory` hinüber, weil das Inventar nach dem ersten Aufsetzen auf dem Manager lebt. Dateien werden einzeln mit bis zu drei Versuchen übertragen; ein `sftp`-Batch mit vielen `put` scheiterte im Pilot lautlos.
* **Manager-Tick einstellbar:** `mgrTick` in `global.rsc` (Standard 10 min) steuert Status-Abholung, Ring-Aufstieg, Secret-Sync, Updates, Netzplan, Hook und Vault-Backup. Das Onboarding läuft auf einem eigenen Scheduler jede Minute, damit eine laufende Sitzung nicht langsamer wird.
* **Integritätsschutz:** Jedes Gerät bekommt ein eigenes Manifest `live/m/<serial>.mf` mit Version, Rolle, Dateiliste + SHA-512 und einem MAC (`sha512(key . sha512(body))`) mit dem beim Onboarding ausgetauschten Geräteschlüssel. Geräte haben am Manager nur Lesezugriff. Der MAC schützt zusätzlich gegen manipulierte Spiegel oder Transportwege: Ein Gerät verwirft jedes Manifest, das nicht mit seinem Schlüssel gesichert ist.
* **Kanalplanung:** Kanal-Pools zentral in `wifi.rsc`, optionales Pinning pro AP ebenfalls in `wifi.rsc → radios`, weil der CAPsMAN (nicht der AP) die Radio-Config rendert. Vorschlag für die Pins per Scan: D56/D60.
* **Inventar ist Metadatum:** `meta/inventory.rsc` (Name, Seriennummer, Rolle, Ring, MGMT-IP) wirkt ohne Release; Inhalte (`work/`) nur per Release.
* **Reihenfolge-sensitive Listen (Firewall/NAT):** werden als Block verwaltet. Bei geänderter Signatur wird der neue Block zuerst eingefügt und dann der alte entfernt (kein Moment ohne Regeln).
* **Werte nie in Code-Strings einsetzen:** Der Reconciler erzeugt Kommandos per `:parse`, übergibt aber alle Werte als Variablen (`name=($P->"name")`). Dadurch gibt es kein Quoting/Escaping und keine Injection über Daten (SSIDs mit Leerzeichen/Anführungszeichen).
* **Geräte-Rückmeldungen nur als Daten:** Status als JSON (`:deserialize`), Audit als Text. Der Manager führt nie etwas aus, das von einem Gerät stammt.
