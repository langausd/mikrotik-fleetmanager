# RouterOS-Eigenheiten

Im CHR-Labor und auf Hardware gefundene Eigenheiten von RouterOS. Die Nummern in der Spalte Konsequenz verweisen
auf [DECISIONS.md](DECISIONS.md).

## Im CHR-Labor verifizierte RouterOS-Eigenheiten (ab 7.24.2)

Diese Punkte haben die Umsetzung geprägt und gelten für eigene Templates:

| Eigenheit | Konsequenz |
|---|---|
| Eine Zeile, die mit `[` beginnt, kann als Fortsetzung der vorigen Anweisung gelesen werden | Funktionsaufrufe als Anweisung immer ohne Klammern: `$cfmEnsure …` |
| **Der Aufruf einer nicht definierten globalen Funktion (`[$cfmXyz …]`) bricht nicht ab, sondern liefert `nothing`** | Manager-Funktionen laufen direkt nach Bootstrap oder Neustart ohne die Helfer aus `lib/lib.rsc` (die setzt sonst erst der Agent beim Apply). `$cfmLoadData` importiert die zur Version gehörende `lib/lib.rsc` mit, `$cfmCheck` meldet fehlende Helfer als Fehler. Gefunden 2026-09-17: `$cfmCheck` hielt mit neuer Policy-Syntax jedes Ziel für eine unbekannte Zone, und die Überschneidungsprüfung WireGuard/VLAN lief seit DR4.1 wirkungslos. |
| Ein String-Literal mit Escape (`\n`, `\"`, `\$`) direkt als Argument einer eigenen Funktion ist ein Syntaxfehler – positionell wie `k="…"`, an der Konsole wie bei `/import` (7.24.5; `:parse` akzeptiert es); eingebaute Befehle (`:pick`, `/file/set`) sind nicht betroffen | in runde Klammern setzen (`$f ("{\"a\":1}")`) oder vorher in eine Local legen; `tools/rsc-check.py` meldet es (`escape-argument`) |
| Ein leeres Array direkt nach `:global`/`:local` (`:global x {}`, auch `{` und `}` auf zwei Zeilen) ist beim `/import` ein Syntaxfehler, weil RouterOS es als Codeblock liest (7.24.5); gefüllte Literale gehen | `({})` schreiben – so in `leases.rsc`; `tools/rsc-check.py` meldet es (`leeres-array`) |
| `:for i from=5 to=4` läuft rückwärts (zweimal), statt gar nicht | Schleifen über eine möglicherweise leere Spanne vorher mit `:if` absichern |
| Pakete in einer RAM-Disk (`/disk add type=tmpfs`, Datei unter `<slot>/`) installiert RouterOS beim Neustart nicht; der Inhalt ist danach weg (CHR 7.24.2) | kein tmpfs-Weg für Geräte mit wenig Flash, stattdessen das eingebaute Update (DV1.5) |
| `/system/package/update` hat `mode=https\|http` und `check-certificate`; mit `mode=http` und einem statischen DNS-Eintrag für `upgrade.mikrotik.com` holt es Versionsdatei, CHANGELOG und Pakete von einem lokalen HTTP-Server (Port 80) | Spiegel für Geräte ohne Internet (DV1.5) |
| `/routing/table/add … fib` ist ein Flag ohne Wert; `fib=yes` ist ein Syntaxfehler, `$cfmRun` kann es deshalb nicht übergeben | Tabelle einmal direkt mit Flag und cfm-Kommentar anlegen, `$cfmEnsure` übernimmt sie über den Schlüssel |
| Nicht vorhandene Menüs in Slash-Schreibweise (`/system/routerboard/…` auf CHR) sind Syntaxfehler, die `:onerror` nicht fängt | geräteabhängige Menüs in Leerzeichen-Schreibweise (`/system routerboard get …`) oder per `:parse` |
| `/import … verbose=yes` führt Zeilen einzeln aus | Locals gehen verloren, nur `verbose=no` verwenden |
| `/user add` verlangt ein Passwort | Benutzer werden mit Zufallspasswort + `disabled=yes` angelegt, bis der Secret-Push kommt |
| SFTP-Zugriff braucht die Policies `ssh,ftp,read`; ein Upload zusätzlich `write` | Gruppe `cfm-dev` bleibt lesend, der Manager holt Rückmeldungen ab |
| Lesende SFTP-Nutzer bekommen auf `*.json` und `*.backup` „Permission denied“ (alle anderen Endungen gehen) | Manager-Dateien für Geräte/Spiegel/Git heißen `*.dat` (Inhalt JSON); das Vault-Backup wird nach dem Speichern in `*.bak` umbenannt |
| `:return` innerhalb von `:onerror … in={}` verlässt die Funktion nicht | Ergebnis über ein Flag setzen und am Ende zurückgeben |
| Dateien mit führendem Punkt tauchen in `/file` nicht auf | keine Dotfiles als Zwischendateien |
| `[:tonum nothing]` ist `nil`, Vergleiche damit sind weder wahr noch falsch; Strings lassen sich nicht mit `<`/`>` vergleichen | Versionen als String vergleichen, Änderungen per md5-Signatur erkennen |
| `capsman enabled` liefert `"yes"`/`"no"` (String, kein Bool) | Vergleich per `[:tostr …] ~ "yes\|true"` |
| Versionen: `/system/resource version` ist `7.24.4 (stable)`, bei Vorabversionen `7.25beta5`; `[:tonum "25beta5"]` ist `nil` | `$cfmVerGe` trennt die Kennung ab und ordnet alpha < beta < rc < fertige Version |
| Adresslisten speichern eine Hostadresse ohne Präfix: `address=192.168.1.5/32` liest `/get` als `192.168.1.5` (String); `/ip/address` behält `/32` | `cfmSame` vergleicht einen Soll-Wert mit `/32` (IPv6 `/128`) ohne Präfix, wenn der Ist-Wert keins hat |
| QEMU-Multicast-Netz spiegelt Frames an den Sender zurück (RSTP blockiert) | CHR-Labor nutzt eine Stern-Topologie mit Punkt-zu-Punkt-Sockets |
| `/tool fetch mode=sftp` nutzt die unter `/user ssh-keys private` importierten Schlüssel | Pull ohne Passwort, Geräte-Identität = exportierter ed25519-Host-Key |
| per `place-before` eingefügte Regeln zeigen ohne explizites `disabled=no` das Flag `I` | `cfmBlock` setzt `disabled=no` |
| `/file get … contents` liest bis ca. 60 KB | `$cfmRelease` weist größere Dateien ab |
| `/import` schreibt nach jeder Datei „Script file loaded and executed successfully“ ins Terminal, auch innerhalb einer Funktion und mit `verbose=no`; `[[:parse [/file/get <datei> contents]]]` lädt still (Labor 7.25.1, 2026-11-05) | Manager-Befehle laden Site-Daten, Hostfiles und Module per `:parse` (bis ~60 KB) |
| `/tool/fetch` per SFTP braucht je Abruf mindestens 1 s, egal ob 0,4 oder 46 KB, ob in eine Datei oder mit `output=user` (CHR 7.24.5, gemessen mit `:time`); ein vergeblicher Versuch je Manager ebenso | Der Agent lädt beim Apply nur geänderte Dateien (DG4.4) |
| Pakete an die VIP (virtuelle MAC) eines VRRP-Interfaces haben `in-interface=vrrp<VID>`, nicht das VLAN-Interface darunter | VRRP-Interfaces in die Zonen-Listen (Rolle `router`) |
| Die Routing-Tabelle einer gerade angelegten VRF steht erst kurz danach bereit; eine Route mit `routing-table=<vrf>` im selben Befehl scheitert | im Labor (`e2e-vrrp.sh`) Routen in einem zweiten Aufruf |
| `/file/find where name=…` prüft jede Datei (CHR 7.24.5, 600 Dateien: 8 ms je Aufruf); `/file/get <Name> …` greift direkt zu (0,05 ms) und wirft „no such item“, wenn es die Datei nicht gibt | Zugriffe auf bekannte Namen per `get`/`set` in `:onerror`, Suchen nur für Muster (DG4.1) |
| Scheduler ohne `start-date`/`start-time` beginnen beim Anlegen (Zeitpunkt + Intervall). RouterOS 7.24 bis 7.24.4: „scheduler scripts with the default start date and time not being triggered“ (Changelog 7.24.5) | betrifft `cfm-watchdog`, `cfm-agent-retry`, `cfm-onboard-revert` und die Bootstrap-Stufen; Labortest des Watchdog-Rollbacks (`e2e.sh` Schritt 14d) |
| Ein Scheduler mit `start-time=startup` **und** Intervall läuft nach einem Neustart erst nach dem ersten Intervall, nicht beim Start | zusätzlicher Scheduler `cfm-agent-boot` (`startup`, ohne Intervall): Der Agent meldet sich 20 s nach jedem Boot |
| `/ip/neighbor`: Nachbarn erscheinen nur, wenn die Nachbarsuche auf den physischen Bridge-Ports läuft; `interface` ist dann eine Liste (`ether2;bridge`), `interface-name` der Gegenseite z.B. `bridge/ether3` | Liste `DISC` mit allen Bridge-Ports; der Agent nimmt das erste Listenelement und den Teil nach `/` |
| `/interface/wifi/security … multi-passphrase-group=""` hinterlässt eine leere Zuweisung | Gruppe per `unset` lösen |
| Nach einem Neustart nimmt eine Bridge mit VLAN-Filtering auf CHR sporadisch keine getaggten Frames ihrer Ports mehr an: RSTP „forwarding“, Konfiguration korrekt, die Frames sind im Sniffer sichtbar, erreichen aber das VLAN-Interface nicht. Im Labor nach `/system backup load` 2 von 2, nach einfachem Neustart 1 von 4 Mal; Aus- und Einschalten des Ports behebt es | Der Boot-Lauf des Agents (`cfm-agent-boot`, Argument `boot`) startet die Ethernet-Ports der Bridge einmal neu, wenn er keinen Manager erreicht. Ob echte Hardware betroffen ist, ist offen ([TESTSTAND.md](TESTSTAND.md#offen-auf-hardware)) |
| Ein Skript per `reset-configuration run-after-reset=` läuft als `*sys`: ohne SSH-Schlüssel (ssh-exec und SFTP-fetch mit Schlüssel: „authentication failure“), was es anlegt, gehört `*sys` (`owner` nicht setzbar). SSH, FTP und HTTP antworten erst, wenn das Skript beendet ist; ein Fehler bricht es ab (Log `system,error,critical`). CHR legt danach selbst wieder einen DHCP-Client auf ether1 an | Bootstrap-Stufe 2 kurz halten und mit `:onerror` absichern; Übergabe an cfm per SFTP-Upload einer `.auto.rsc` mit Einmal-Passwort nach dem Hochfahren (DO3.1) |
| Verbindungen eines Geräts zu seiner eigenen Adresse laufen durch die input-Chain, kommen aber nicht über das Interface dieser Adresse herein (`in-interface-list` greift nicht) | Die Router-Firewall akzeptiert `src-address-type=local`; sonst scheitern auf einem Gerät mit Router- und Manager-Rolle Status-Abholung, Agent-Pull und Watchdog-Bestätigung an die eigene MGMT-IP, und der Watchdog rollt zurück |
| `/system/ssh-exec` bricht lange Befehle mit „action timed out“ ab | Lange Aktionen auf dem Gerät per `:execute` starten, Ergebnis per SFTP abholen (`$cfmPlan`); Pakete lädt der Agent im eigenen Lauf |
| `/system/package/downgrade` startet im Skript sofort und ohne Rückfrage neu – auch ohne passende Pakete | Der Agent ruft es nur auf, wenn alle Pakete geladen und in der Größe geprüft sind |
| Globale Variablen über die API (7.24.5): `/system/script/environment` liefert nur Usern mit `write` **und** `policy` Einträge (`read,api,test` auch mit `sensitive`, `write` oder `policy` allein: leer). Ein per API gestartetes Skript (`/system/script/run`) ändert keine globale Variable, auch nicht als `full` und mit `dont-require-permissions`; Konsole und Scheduler schon. Jede API-Abfrage meldet sich an und ab (zwei Zeilen `system,info,account` im Log) | Zustand für API-Clients nie in globale Variablen legen, sondern aus Konfiguration oder Datei lesen lassen (`/file/print ?name=… =.proplist=contents` geht mit `read`); DW4.1: `tools/home-assistant/cfm_ssid.py`, Abfrageintervall ≥ 5 min |
| `/user/ssh-keys` (7.24.2, 7.24.5): `add user=<u> key="<OpenSSH-Zeile>"` legt den Key direkt an und liefert die ID; der Kommentar landet in `info`, lesbar ist `fingerprint` (`SHA256:<base64>`). Kein `set`, kein `comment`; Typen nur `rsa`, `ed25519`, `ed25519-sk` (ecdsa nicht); ein kaputter Key scheitert mit „unable to load key file“. `:convert` kennt kein SHA-256 | Abgleich der Admin-Keys über den Fingerprint durch Anlegen und gleich wieder Entfernen (DS3.3); `$cfmCheck` lässt nur die drei Typen zu |
| `/system/package` zeigt installierte Pakete mit `available=false`, `disabled=false`; `architecture-name` ist z.B. `x86_64` (Paketname ohne Suffix) oder `arm64` | Status meldet `arch` und `pkgs`, Paketname `<pkg>-<ver>[-<arch>].npk` |
| `:deserialize from=json` deutet Strings um (7.24.5): `"7.24.5"` → IP `7.24.0.5`, `"7.25"` → `7.0.0.25`, `"01234567"` → `1234567`, `"007"` → `7`, `"0x1F"` → `31`, `"yes"`/`"no"` → Bool, `"10m"` → `00:10:00`, `"1:30"` → `01:30:00`, `"2026-10-01"` und `"2026-09-13 01:21"` → Zeitwert, `"10.0.0.0/8"` → Präfix; Text mit Leerzeichen oder Buchstaben (`"7.25rc1"`, `"7.24.5 (stable)"`, `"switch,ap"`) bleibt Text. `:serialize` schreibt Ziffern-Strings als Zahl | Werte, die einen JSON-Umlauf überstehen müssen, bekommen ein Präfix (`"rv"="v7.24.1"`, `"at"="@2026-…"`), das beim Lesen wieder abgeschnitten wird; `tools/rsc-check.py` Regel `json-typ` (DV1.6) |
| RouterOS 7.25 meldet `/system/resource/get version` ohne Kanal (`7.25rc1`, laut Changelog „remove the channel label“); 7.24 lieferte `7.24.5 (stable)` | Der Agent hängt den Kanal aus `/system/package/update` an, wenn kein Leerzeichen vorkommt; der Manager schneidet wie bisher beim ersten Leerzeichen ab |
| RouterOS 7.25rc1: `/ip/ssh` hat `known-hosts-validation` (frisch installiert und nach Reset `yes`, nach einem Update von 7.24 `no`) und `known-hosts-trusted-subnets`; `/ip/ssh/known-hosts/add host= key="ssh-ed25519 …"`. Mit `yes` scheitern `/tool/fetch mode=sftp` und `/system/ssh-exec` an unbekannten Hosts („host key not trusted“). Nach Reset ist der Host-Key ed25519 und neu. Eine unbekannte Property in einem nicht ausgeführten Zweig stört 7.24 beim Parsen nicht | DS1.5 |
| REST (7.25rc1, über `www`): `GET /rest/file` liefert keinen Inhalt; `POST /rest/file/get {".id", "value-name":"contents"}` liefert ihn unverändert; `PATCH /rest/file/<id> {"contents"}` schreibt UTF-8 korrekt, bis knapp 60 KB (64 KB → 400); `POST /rest/execute {"script", "as-string":true}` gibt die Ausgabe zurück, ohne `as-string` nur die Job-ID; `:execute script=… file=…` schreibt die Ausgabe laufend in die Datei. Keine CORS-Header, `OPTIONS` → 503 | DT3.1 |
| WebFig (7.24.5 und 7.25rc1) zeigt unter „Files“ keinen Inhalt zum Bearbeiten. Im WebFig-Terminal geht `/file/edit <datei> contents`: unverändert gespeichert bleibt die Datei Byte für Byte gleich, vorhandene Umlaute bleiben (Anzeige verstümmelt), eingetippte Nicht-ASCII-Zeichen verwirft der Editor | DT3.1 |
| Bridge-Filter bei VLAN-Filtering: VLAN-Matcher (`vlan-id`, `vlan-encap`) greifen nur für getaggt angekommene Frames, IP-/ARP-Matcher sind nur ohne `mac-protocol=vlan` erlaubt. Einen ungetaggt angekommenen Frame (Access-Port mit PVID) sieht der Filter je nach Karte als `ip`/`arp` (virtio) oder als `vlan` (e1000) – dann greift keine IP-Regel (7.24.5 und 7.25rc1, Labor 2026-10-12) | Isolation (DP3.1) filtert am Eingang der Client-Ports (Interface-Liste), das Gateway erkennt sie an der MAC (VRRP-MAC, Bridge-MACs der Router); wie echte Switch-Chips und WLAN-Treiber die Frames zeigen, ist offen ([TESTSTAND.md](TESTSTAND.md#offen-auf-hardware)) |
| `/interface/vlan` hat keine eigene MAC-Adresse (`bad parameter mac-address`), VLAN-Interfaces nutzen die MAC der Bridge | Der Agent meldet die Bridge-MAC (`mac` im Status), DP3.1 nimmt sie als Router-MAC |
| `/queue/type` kennt kein `comment` („bad parameter comment“, 7.25); einen benutzten Typ löscht RouterOS ohne Fehler, die Simple Queue zeigt danach `*<id>` statt des Namens. `pcq-rate` liest `get` als Zahl, `max-limit` als Text in eigener Schreibweise (`1500000` → `1500k`, `1000k` → `1M`, `12345678` bleibt) | `cfmByName` (Schlüssel = Name „cfm-…“), Queues vor Typen aufräumen, `rateFmt` in `lib/router.limit.rsc` (DR2.7, bis DG4.6 `$cfmRateFmt`) |
| CHR-Lizenz `free`: 1 Mbit/s je Interface (`bandwidth-test` ~1,0–1,1 Mbit/s). Fasttrack markiert Verbindungen, der Fast Path bleibt aber aus (`/ip/settings` `ipv4-fast-path-active: no`, `ipv4-fasttrack-packets` 0) – Verkehr läuft trotz Fasttrack durch Simple Queues | Durchsatz im Labor nur unter 1 Mbit/s messen; ob Fasttrack Queues umgeht, nur auf Hardware prüfbar (DR2.7) |
| LACP zwischen CHRs mit virtio-Karten: `key=0`, nur ein Port synchron, der zweite bleibt inaktiv (Peer-Bond wie Bond zum Server, 7.24.5 und 7.25rc1). Mit e1000 (1 Gbit/s Vollduplex) `key=9`, alle Ports aktiv | `e2e-mlag.sh` setzt `LABNIC=e1000` (`lab.sh`) |
| Ein im Gast abgeschaltetes Interface meldet der Gegenseite über die QEMU-Socket-Verbindung keinen Link-Ausfall; RouterOS hält einen 802.3ad-Port ohne LACP-Pakete weiter für aktiv | Ausfälle im Labor an beiden Enden nachstellen (`e2e-mlag.sh` Schritt 6) |
| `/interface/bonding/monitor-slaves` liefert über eine SSH-Befehlszeile nichts und kennt kein `once` | im Hintergrund per `:execute … file=` laufen lassen, Job beenden, Datei lesen (`e2e-mlag.sh`, `lacp()`) |
| REST (7.24.5): Die erste Anfrage eines Users schreibt `user … logged in from … via rest-api` (und `via api`) ins Log, weitere Anfragen kurz danach keine neue Zeile; `GET /rest/system/clock` liefert `date` als `2026-10-12`, `time` als `21:06:21`; `POST /rest/log/print` mit `.proplist` geht; `/interface/wifi/registration-table` gibt es auch auf CHR (leer) | Das Lesezeichen „cfm-WLAN“ (DU2.2) fragt regelmäßig ab, ohne das Log mit Anmeldungen zu füllen |
| REST (7.24.5): Antworten tragen `Cache-Control: max-age=31536000` (WebFig selbst `no-store`) – der Browser lieferte wiederholte GET-Abfragen aus dem Cache (alte Uhrzeit, alte Registrierungstabelle; Hardware 2026-10-14) | Lesezeichen (DT3.1, DU2.2) fragen mit `fetch(…, {cache: 'no-store'})` ab |
| WebFig/REST (7.24.5, Firefox): REST ohne `Authorization` → 401 mit `WWW-Authenticate: Basic`, der Browser zeigt seinen Anmeldedialog und schickt die Daten danach auch bei `fetch` ohne Kopf mit; nach einem Abbruch oder Tippfehler fragt Firefox nicht erneut. `XMLHttpRequest.open(…, user, pass)` öffnet nie den Dialog: 200 legt die Daten im Browser ab (danach `fetch` ohne Kopf 200), 401 ersetzt sie (danach 401 ohne Dialog), erneut richtig stellt sie wieder her. WebFig hält nach dem Login nur ein Token in `localStorage` (`token`), kein Passwort; REST lehnt das Token ab (Bearer und Basic → 401). Aus der WebFig-Seite sind `session`, `fetchFile` und `request` global erreichbar: Lesen per `/jsproxy/?<verschlüsselt>`, Schreiben per `/jsproxy/put` (UTF-8 korrekt, so speichert WebFig auch Skins), ein unsichtbares `Terminal` führt Befehle aus (frische CHR fragt erst nach der Lizenz; eingetippte Umlaute fallen weg). Skins sind reine JSON-Dateien in `skins/` | DT3.1: Anmeldung per Formular und XHR |
| Firefox (153 ESR) legt ein Lesezeichen über 65 536 Zeichen nicht an (Places: „Invalid value for property 'url'“); cfm-Monitor hatte nach DU1.4 so 73 700 Zeichen und ließ sich nicht installieren, cfm-WLAN mit 52 000 noch | `tools/editor/build.py` lässt Kommentarzeilen, Einrückung und Leerzeilen weg und kodiert in URLs erlaubte Zeichen nicht mehr (cfm-Monitor 47 200, cfm-Editor 21 400 Zeichen); über 60 000 bricht der Bau ab. Geprüft: Anlegen per Places-API im Firefox, alt abgelehnt, neu unverändert gespeichert |
| RouterOS 7.25rc1: Ein über die API gestartetes Skript setzt `:global`-Variablen in der gemeinsamen Umgebung (7.24.5: nicht), lesen kann `/system/script/environment` weiterhin nur ein User mit `write` und `policy` | Gast-Schalter (DW4.1) bleibt beim Zustand aus den Regeln; `cfmSsid<key>` stimmt ab 7.25 auch nach dem Schalten aus HA |

## Auf Hardware verifizierte RouterOS-Eigenheiten

Im Hardware-Pilot (CRS418, hAP ax²) und beim Rollout an einem zweiten Standort (hAP be³, cAP ax, hAP ax³, CRS328, hEX) gefunden; sie gelten zusätzlich zur Tabelle oben.

| Eigenheit | Konsequenz |
|---|---|
| Jedes Setzen unter `/interface/wifi/cap` – auch auf den Standardwert (`slaves-static` von „nicht gesetzt“ auf `no`, 7.24.4/7.25beta5) – trennt den CAP vom CAPsMAN („configuration changed“) und baut die Verbindung neu auf (3–24 s) | nur setzen, was sich wirklich ändert; der lokale Fallback (DW1.6) überbrückt die Haupt-SSID |
| Der SFTP-Server von RouterOS antwortet auf `mkdir` für ein vorhandenes Verzeichnis mit „Unknown status“ (Zeile endet mit CR) statt „already exists“ | `upload-seed.sh` blendet genau diese Meldungen aus |
| Die Bridge eines Virtualisierungshosts reicht BPDUs aus dem Netz an die VMs durch; auf einem Port mit `edge=yes` schlägt dort der BPDU-Guard zu und schaltet ihn ab (nur ein manuelles Aus/Ein bringt ihn zurück) | Für Karten virtueller Maschinen das Profil `vport:<vid>` statt `access:<vid>` – gleiche Wirkung, aber ohne Edge und BPDU-Guard (2026-09-20 am virtualisierten Manager aufgelaufen; betroffen war die Karte im ungetaggten VLAN, weil RSTP ungetaggt spricht) |
| Ein `reset-configuration` setzt `host-key-type` auf `rsa` zurück, `keep-users=yes` behält aber die privaten Benutzerschlüssel | Der Bootstrap stellt den Typ jetzt unabhängig davon auf ed25519 und ersetzt dann die privaten Schlüssel; der Export wird geprüft, statt später mit „no such item“ zu scheitern (2026-09-20 beim Neuaufbau eines Managers mit `clean="no"`) |
| `find` liefert auch dynamische Einträge, z.B. vom Switch-Chip angelegte `/interface/bridge/vlan`-Einträge, sobald viele Ports gleichzeitig eine neue PVID bekommen (CRS418); ein `set` darauf scheitert mit „can not change dynamic“ | `$cfmIds` (bis 2026-10-16 `$cfmFind`) sucht immer mit `!dynamic`; eigene Templates, die `find` direkt nutzen, ebenso |
| `/system/logging/add` mit `comment` scheitert auf manchen Builds mit „expected end of command“ (hAP ax², wifiwave2), auf dem CRS418 nicht | `base` legt die vier Syslog-Einträge ohne `comment` an und findet sie über `action` und `topics`, nicht per `$cfmEnsure`; an den Standardregeln ändert es nur die Topics von `info` → memory (DU3.2) |
| Löscht man eine `/system/logging/action`, auf die Einträge zeigen, bleiben die Einträge als ungültig (`I`, Aktion `*5`) stehen; `find where action="cfmremote"` trifft danach auch die Standardregeln (RouterOS 7.25, Labor) | `base` entfernt zuerst die Einträge, solange die Aktion existiert; die Aktion entfernt danach die GC |
| Neue RouterBOARD-Firmware flasht `auto-upgrade` beim Neustart nach einem RouterOS-Update, aktiv wird sie erst nach einem weiteren Neustart; ohne ihn bleibt `upgrade-firmware` dauerhaft ungleich `current-firmware` (hAP ax²) | Der Agent erkennt den Unterschied und startet einmal neu, per `:parse`, weil `/system/routerboard` auf CHR/x86 fehlt |
| `auto-upgrade=yes` flasht nur beim Neustart direkt nach einem RouterOS-Update. Lief das Update, bevor `auto-upgrade` an war (Onboarding aktualisiert RouterOS vor dem ersten Apply), bleibt die Firmware alt (hAP ax²: 7.16.2 statt 7.24.4); der Agent startete daraufhin nach jedem Boot neu, alle 1–2 min, ohne dass der Manager noch einen Status abholen konnte | Der Agent flasht selbst (`/system/routerboard/upgrade`) und startet je Firmware-Version höchstens einmal neu (`fw` im Status); wirkt es nicht, Fehler im Log und `fw X!` in `$cfmStatus` statt einer Schleife |
| Die erlaubten Adressen der IP-Dienste (`/ip/service … address=`) wirken unabhängig von der Firewall: WireGuard-Peers, die die Firewall als Zone `mgmt` durchlässt, weist SSH/Winbox trotzdem ab | `base` nimmt das WireGuard-Subnetz in die erlaubten Adressen auf, der Router zusätzlich in `cfm-mgmt` (DR4.1) |
